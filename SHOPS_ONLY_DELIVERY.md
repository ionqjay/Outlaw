## Bounded reconciliation worker — implemented, not deployed
Supersedes the earlier missing-scheduler note. The existing long-running Express process now has an opt-in internal billing reconciliation timer; no public cron endpoint, URL secret, OS scheduler edit or hosting setting was added. Configure only after staging verification and all three pending migrations:

- BILLING_RECONCILIATION_INTERVAL_MINUTES=15 (integer 5–60).
- BILLING_RECONCILIATION_BATCH_SIZE=10 (integer 1–20).
- Existing Supabase service configuration and Stripe secret/shop price required; no new credentials.

Run on ONE persistent backend replica for the pilot. The timer runs once at startup, then each interval, skips overlapping runs, queries only the oldest due bounded batch, and retrieves Stripe subscriptions serially with 10-second timeout/no automatic retries. HTTP 429 stops the batch and honors Retry-After with at least one configured interval. Database failures log and retry on later ticks: if invalidation itself cannot persist, prior cache remains bounded by its existing 24h expiry. An unavailable/sleeping process does not run timers; free Render sleep means this is NOT a durable scheduler guarantee. Capacity and uptime must be monitored; one default worker processes at most 960 records/day, sufficient only for this bounded pilot. Multi-replica distributed claiming and alert delivery remain roadmap items.

## Request-security slice — local implementation only
Express trust proxy is explicitly false by default. Rate limits use Express req.ip, never raw X-Forwarded-For. Optional TRUSTED_PROXY_CIDRS accepts only explicit comma-separated IPv4/IPv6 proxy addresses or nonzero CIDRs; booleans, hop counts and all-address /0 ranges are rejected. Determine the real trusted last-hop networks and ensure the ingress appends/overwrites forwarding headers BEFORE configuring this in staging/production. No proxy hop count or Render CIDR was assumed. With default trust off, users behind the same reverse proxy/NAT share a budget: secure but potentially restrictive. This must be validated before deployment.

The per-process limiter runs before route handlers/body parsing and uses bounded 10,000-entry fixed one-minute windows, lazy expiry, and refuses new buckets at capacity rather than evicting existing budgets. Case-insensitive route normalization prevents mixed-case Express route bypass. OPTIONS is exempt; health/static assets and signed Stripe webhooks are outside the IP limiter. Coverage includes requests, quotes, signup/public owner requests, billing, provider/history, admin, feedback and notifications. Multi-instance/global quotas and per-account limits remain future work; this is not DDoS protection. No settings changed remotely.

Validation now bounds typed repair, vehicle, quote and registration text; validates year/state/ZIP/category/urgency; strips metadata/parts envelope when measuring symptom length; and covers both authenticated and public owner-request routes. Contact fields on public submissions are validated. Registered business references remain free-form evidence, not legal verification. Server-derived quote names are not rejected based on discarded client names. JSON over 100kb returns 413; malformed JSON returns 400. Owners remain free and history endpoints unchanged.

Independent review identified and fixed mixed-case rate-limit bypass, missing public-owner validation, metadata-inflated symptom length, conflicting quote-name limits and invalid state codes. ## Repair status workflow — local implementation, not deployed
Accepted quote providers can Start work (accepted → in_progress) and Request owner completion confirmation. The completion request is a timestamp on in_progress, not a destructive status conversion. Only the repair owner can confirm completion or indicate work is not complete yet. Existing owner direct completion from accepted/in_progress remains supported for backward compatibility. Accepted historical providers (including legacy mechanic identities/expired subscriptions) retain workflow access for their actual accepted job; no new leads or subscription privileges are granted.

Cancellation now consistently permits only open requests, including admin override; replay of an already cancelled request is idempotent. Accepted/in-progress/completed jobs cannot be cancelled through this endpoint. This closes the previous accidental cancellation of in-progress/completed jobs, without inventing dispute, liability or refund policy. No automatic billing or refund actions.

Migration 20261021050000_repair_workflow.sql adds completion_requested_at, workflow_revision and service-only immutable transition events. SQL transition RPC locks the repair row, rechecks participant/action/current state, atomically updates repair/bid cancellation state and appends history. Acceptance RPC now records acceptance in the same transaction. New workflow controls supply expectedRevision; delayed completion-request/continue-work commands cannot reverse a later decision. Conflicts require refresh rather than silent overwrite. Historical records are not rewritten or backfilled.

Authorized owners and existing quote participants may read the most recent 50 events via /api/repairs/:id/transitions, without exposing actor account IDs. Transition rows RESTRICT parent repair deletion, preserving history until an explicit retention/deletion policy is approved. Existing admin removal may therefore be blocked for repairs with history/photos; do not bypass these constraints to delete records.

Local development retains synchronous read/validate/write critical sections and atomic single-file replacement. Cancellation retries repair interrupted bid-decline persistence.
